# 私聊文案与投稿流程重构 RFC

> Phase 对齐：纯 UX/文案重构，不改变数据模型、命令集、状态机或对外回调契约。
>
> 状态：Telegram 文案契约 `IMPLEMENTED`；Mini App 移动端视觉基线 `IMPLEMENTED`；
> 真人 Telegram / Mini App 验收 `EXTERNAL_ACCEPTANCE_REQUIRED`。

## 1. 目标

私聊体验要达到「打开 /start 就知道能做什么、开始 /submit 就知道下一步、
预览页一眼可改、发完知道发生了什么」。

现状问题：
- 文案散落各 handler，风格不统一（Emoji、标点、分段、引导步骤各写各的）。
- 错误提示只报错不给下一步恢复路径（如「会话已过期」未提示重新 /submit）。
- 预览页信息堆叠，主次不清；修改/发布按钮与字段说明割裂。

## 2. 统一排版规范

- 每条消息首行 = 场景 Emoji + 粗体标题（`<b>…</b>`）。
- 段与段之间空一行，短清单用 `•`，步骤用 `1️⃣ 2️⃣ 3️⃣`。
- 关键值（数量、命令、状态）用 `code` 或粗体，避免长句混排。
- 需要用户回应时，最后一行必须给出明确下一步动作。
- 错误消息带恢复建议（如「请发送 /submit 重新开始」）。
- 保留既有稳定子串（`已接收媒体/文件`、`发布预览`、`提交审核`、`标签已更新`
  等），避免破坏集成测试与用户肌肉记忆。

## 3. 投稿流程状态机与消息映射

| 阶段 | 触发 | 消息要点 |
| --- | --- | --- |
| 入口 | `/start` | 欢迎 + 一句话价值 + 快速开始按钮 + 命令速览 |
| 提交 | `/submit` / 菜单「开始投稿」 | 模式提示 + 1-2-3 步骤 + `/done_media`/`/cancel` |
| 上传 | 收到媒体/文档 | 已接收 + 当前计数 + 下一步（继续/预览/取消） |
| 上传 | 收到文字/非法格式 | 阐明只收媒体 + 预览/取消位置 |
| 预览 | `/done_media` | 字段化预览 + 修改按钮 + 发布/审核按钮 |
| 编辑 | 编辑回调 | 统一「发送新值 / 回复『无』清空」提示 |
| 完成 | 发布/入审核 | 明确去向（频道 or 审核队列）+ 是否会收到通知 |

## 4. 落地范围

- `ui/messages.py`：集中 `start`/`help`/`submit_hint`/`upload_*`/`preview`
  /`edit_*`/`done_*` 文案，新增通用错误恢复文案。
- `handlers/mode_selection.py`、`handlers/upload.py`、
  `handlers/preview_handlers.py`、`handlers/command_handlers.py`：改用集中文案，
  删除散落重复字符串。
- 保持现有 ConversationHandler 状态（UPLOAD → PREVIEW → EDIT）与命令集不变。

## 5. 验收

- 全量测试通过。
- 集成测试断言（`已接收媒体`、`发布预览`、`标签已更新`、`进入审核队列`）仍成立。
- 新增单测验证：start / submit_hint / upload 提示 / 预览文本 / 编辑提示 含规范元素
  （Emoji 标题、下一步动作、错误恢复建议）。
